# 운영 시뮬레이션 가정값·근거표 (4번)

작성 기준: `menu_catalog.json`, 을지로입구 상권 원본(`data/public/seoul_sales_euljiro_coffee_2024q1_2026q2.csv`)과 전처리 결과(`ai-server/app/tools/simulation/data/demand_shares.json`), SOLution `data/demo/` 계약. **실측 카페 판매/제조 통계가 아닌 시연용 가정**임.

## 시간과 수요

| 시뮬레이션 구간 | 고객 수요 비중 | 근거/주의 |
|---|---:|---|
| 07:00–11:00 | 32.82% | 06–11시 자료의 4/5 추정 |
| 11:00–14:00 | 49.68% | 11–14시 원 구간 |
| 14:00–17:00 | 14.81% | 14–17시 원 구간 |
| 17:00–19:00 | 2.68% | 17–21시 자료의 2/4 추정 |

출처: 서울시 상권분석서비스 *커피·음료* 업종의 을지로입구역 상권 시간대별 **카드 결제 건수**. 적용 기간 2024Q1~2026Q2 10분기 P50. 시간대 일부를 균등 분할한 것은 분석상 가정이며, 4구간 반올림 합계 99.99%는 계산 시 정규화하여 처리한다. 상권 결제 건수를 특정 카페 주문량으로 사용하지 않는다. 하루 주문량은 사장님 입력 또는 시연 예제.

시뮬레이션 범위 07–19시. 라스트 오더 기본 18:45, 사용자 화면에서는 18:30~19:00(5분 단위)만 고른다(17시 이후 손님 비중 2.68%라 더 일찍 닫아도 비교 의미가 작음). 이후 주문 수요는 다른 시간대로 이월하거나 재분배하지 않고 **접수 거절 수요**로 기록하며, 이미 받은 주문은 끝까지 처리한다.

### 하루 주문 건수 예시 (화면 빠른 선택용)

개별 카페의 실제 주문 건수는 확인할 수 없어 아래 값은 모두 **모의 실험용 조건**이다. 주문 1건 = 고객 1명 = 음료 1잔으로 가정한다.

| 버튼 | 건수 | 근거 |
|---|---:|---|
| 60건 · 100건 · 150건 | 한산 · 보통 · 혼잡 | 검증용 가상 부하 조건 (데이터 근거 없음) |
| 상권 평균 276건 | 276 | 을지로입구 카페 상권의 점포당 하루 결제 건수 추정치 중앙값 (기존 부하 테스트 240/300건 대체) |

276건 산출 (출처: 서울시 상권분석서비스 점포·추정매출, `서울시_상권분석서비스_점포상권_2024-2026Q2.csv`, `을지로입구_카페상권데이터_2024-2026Q2.csv`. 사용 기간 2025Q1~2026Q2 6분기):

- `07~19시 결제 건수 = 06~11시 × 0.8 + 11~14시 + 14~17시 + 17~21시 × 0.5` (구간 안 균등 발생 가정)
- `점포당 하루 결제 건수 = 07~19시 월 추정 결제 건수 ÷ 전체 점포 수 ÷ 30.44` (30.44 = 연평균 월 일수, 휴무일 미반영)

| 기간 | 점포 수 | 점포당 하루 결제 건수 |
|---|---:|---:|
| 2025Q1 | 78 | 251.2 |
| 2025Q2 | 77 | 286.9 |
| 2025Q3 | 77 | 309.5 |
| 2025Q4 | 73 | 264.6 |
| 2026Q1 | 71 | 261.6 |
| 2026Q2 | 69 | 306.8 |

중앙값 (264.6 + 286.9) ÷ 2 = 275.75 → 276건. 시간대 배분은 위 비중으로 91 / 137 / 41 / 7건.

한계: 매출 CSV의 `당월_매출_건수`를 월 건수로 해석했고 집계 기준은 추가 확인이 필요하다. 카드 결제 기준이라 현금 결제는 빠지고, 결제 1건에 음료가 여러 잔일 수 있다. 2024년은 전체 점포 수와 세부 점포 수 합계가 맞지 않아 제외했다. 276건 산출 기간은 시간대 비중 산출 기간(2024Q1~2026Q2)과 별개다.

| 메뉴 | 비중 | 대표 제조시간 | 근거 종류 |
|---|---:|---:|---|
| 아이스 아메리카노 | 48% | 60초 | 일부 공개 영상 참고 + 모형 가정 |
| 아이스 녹차라떼 | 12% | 75초 | 파우더 사용 전제의 가정 |
| 아이스 카페라떼 | 23% | 70초 | 일부 공개 영상 참고 + 모형 가정 |
| 핫 카페라떼 | 7% | 95초 | 일부 공개 영상 참고 + 모형 가정 |

기본 5종 비중/시간을 보존했다. 모델의 제조단계·에스프레소·스팀·블렌더 점유는 `ai-server/app/tools/simulation/menu_catalog.json`에 정의돼 있다. 10종 후보는 개발자 화면의 **가정 프리셋**일 뿐, 실제 메뉴 판매비중 아님. 메뉴별 제조시간은 공식 업계 표준·엄밀 실측이 아님.

## 공정시간·자원

- 주문·결제 평균 **60초** (민감도 45초), 전달 평균 **30초** (민감도 20초).
- 제조시간은 메뉴별 값, 표준편차·조립 단계는 JSON 카탈로그에 있음.
- 직원은 주문/제조/전달 작업과 에스프레소·스팀·블렌더를 공유. 장비는 별도의 점유 자원.
- 일부 처리 단계는 노동/장비가 동시에 필요하지 않으며 실제 공정 관측 결과라고 주장하지 않음.

## 운영안·비용

- CURRENT: 2명, 역할 고정. ALT_A: 2명, 바쁜 시간에만 상호 지원. ALT_C: 바쁜 시간 3명, 나머지 2명. 엔진 자체 세 안은 바쁜 시간 11–14시 고정(팀 결정 11.11), Spring 근무표를 받을 때는 사장님이 고른 바쁜 시간(기본 11–14시)을 따른다.
- 기본 직원 배치 인시: CURRENT/A 24인시, C 27인시(07–19시). 직원별 교대시간/휴게/사장님 노동/유급 인시로 해석하지 않는다.
- 시뮬레이션 구간(고객 수요)과 인력 배치 구간은 독립 개념. 현재 공개 API는 세 안만 비교, 자유 입력 시프트/30분 조정은 미구현.

## 임시 품질 기준

1. 하루 및 충분한 도착 주문(최소 10건)이 있는 각 구간의 **주문 종료→음료 수령 P90 ≤300초**.
2. **접수된 주문의 19시 완료율 ≥95%**, 품질 판정에 반영 (v1 기본 설정으로 복원, 팀 확정 필요).
3. 반복 30회 중 **80% 이상**이 각 조건을 통과해야 추천 후보.
4. 후보 중 기존 독립 시연판의 `마감 이후 가상 처리 포함 인시 → 인원 변경 횟수 → 평균 주문 후 수령시간` 순서.

위 수치는 업계 표준이 아니라 모형 실험의 임시 목표다. 시간대별 소표본 및 마감 이후 가상 처리를 설명과 함께 표시한다.

## 팀 `data/demo/`와의 관계

- `time_slots.csv`: `slot_id,start_time,end_time,customer_share_pct,staff_count,source` 유지. 직원 칸이 비어 있으면 **0으로 해석하지 않음**.
- `operation_conditions.json`: `daily_customers_ea`, `simulation_runs`는 시연 기본 설정. `daily_customers_ea=null`은 입력 누락이므로 실제 계산에서는 질문 필요.
- `process_times.csv`, `menus.csv`: 기존 팀 공유 헤더 유지. 아직 원본 파일의 공란을 임의로 채우지 않았다. 현재 엔진은 독립 시연판 카탈로그/상권 자료를 기본값으로 사용; 이식 후 실제 공동 메뉴 데이터와 **ID·수치 동기화 작업** 필요.
- 매입 쪽 `sales_recent.csv`와 추정 잔수는 성격이 다르며 섞어 쓰지 않는다.

## Spring 운영 계산과 연결 (근무표 받기)

Spring 운영 계산은 입력에 저장된 근무표(`labor.plans`, 세 안)를 보내고, 엔진은 **받은 근무표 그대로** 손님 흐름을 돌린다.

| 업무 코드 | 엔진 역할 (앞이 먼저, 뒤는 도울 수 있는 일) |
| --- | --- |
| `ALL_TASKS` | 주문·전달·제조를 들어온 순서대로 |
| `ORDER_HANDOFF` | 주문·전달 |
| `PREPARATION` | 제조 |
| `ORDER_HANDOFF_HELP_PREPARATION` | 주문·전달, 한가하면 제조 |
| `PREPARATION_HELP_ORDER_HANDOFF` | 제조, 한가하면 주문·전달 |
| 직원별 형식 `ORDER`·`MAKE`·`FLEX` + `can_support` | 기본 역할 + 지원 업무 |

- 근무 시각은 07:00~19:00 안만 손님 흐름에 영향을 준다. 휴게는 시뮬레이션에 넣지 않는다(labor 배치표에서만 다룸).
- 19:00 마감까지 일하는 사람이 없으면 받은 주문을 끝낼 수 없으므로 계산하지 않고 근무표를 묻는다.
- 응답은 Spring 계약(API 명세 v0.4) 모양이다. 지표 7개는 30회 반복마다 하루 값을 구해 평균했고, 비교는 같은 손님 흐름의 쌍대 차이(주문 후 수령 평균)와 95% 신뢰구간이다.
- 추천 규칙은 위 품질 기준(주문 후 수령 P90)과 같다. 계약의 `basis_metric`에는 가장 가까운 지표인 `post_order_wait_over_300_ratio`를 적고, 실제 규칙은 `recommendation.quality_rule`에 남긴다. 기준을 넘는 안이 없으면 추천은 `null`이고 참고 경고(`NO_FEASIBLE_PLAN`)를 준다.
- 정해 둔 세 운영안 기준의 시간대별 추천은 근무표를 받은 계산에서는 만들지 않는다.

## 확장 예정 (1차 이후)

- 지금(1차)은 Spring이 세 안의 근무표를 먼저 만들고, 서로 돕기·한 명 추가는 바쁜 시간에만 적용한다.
- 원래 설계이자 다음 단계는 **하루 전체 구간에 적용**하는 방식이다: 시뮬레이션이 07~11·11~14·14~17·17~19시 구간마다 목표를 넘는 가장 적은 인원 안(현재·서로 돕기·한 명 추가)을 고르고, 그 조합을 노동 시뮬레이션이 받아 근무표·휴게·인건비를 만든다. 엔진의 시간대별 추천(`slot_plan.py`)이 이미 이 계산을 한다.
- 이렇게 바꾸려면 계산 순서(시간대별 추천 → 근무표 → 노동)와 네 번째 안(시간대 맞춤)을 받는 결과 형식을 Spring과 맞춰야 한다. 바뀌면 이 문서의 "운영안·비용"도 같이 고친다.
